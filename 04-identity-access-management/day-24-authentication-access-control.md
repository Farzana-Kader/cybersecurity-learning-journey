Day 24 — Authentication & Access Control Models


1. Learning — Detailed study notes

1.1 Authentication: how systems verify identity

Authentication is the process of verifying that a user, device, or service is genuinely the identity it claims to be.

Common authentication methods include:

- Password: A secret the user knows.
- PIN: A numeric or alphanumeric secret, often used locally with a device.
- One-time password (OTP): A temporary code, often generated by an authenticator app or sent through a communication channel.
- Security key: A physical device that can provide phishing-resistant authentication.
- Biometrics: Fingerprint or facial recognition.
- Certificate-based authentication: Uses a digital certificate and its associated private key to establish identity.

No method is perfect. A password can be stolen or guessed, an OTP can be phished, and a biometric system can have implementation weaknesses.

1.2 The three authentication factor categories

Authentication factors fall into three main categories.

Factor	Meaning	Examples

Something you know	Information you know	Password, PIN

Something you have	A physical or digital possession	Security key, authenticator device

Something you are	A biological characteristic	Fingerprint, face recognition

Important distinction: Using two factors from the same category does not constitute multi-factor authentication.

For example:

- Password + PIN = two knowledge-based secrets, not MFA by themselves.
- Password + security key = two different factor categories.
- Password + fingerprint = knowledge plus inherence.

A device may also use a local PIN or biometric to unlock a cryptographic credential. In that situation, the local verification can be part of a stronger authentication design; it should not automatically be treated as a separate remote factor without understanding the implementation.

1.3 Single-factor authentication versus MFA

Single-factor authentication (SFA) relies on one authentication factor, such as a password alone.

Multi-factor authentication (MFA) requires two or more different authentication-factor categories.

Consider an employee signing in to a company portal.

1. They enter their password.
2. They approve a security-key challenge.
3. The service validates the authentication and establishes a session.

If correctly implemented, this can make stolen passwords alone insufficient for access.

MFA is especially valuable for administrator accounts, remote access, email accounts, cloud services and systems containing sensitive information.

However, MFA does not eliminate all risks. Session theft, phishing, compromised devices and weak account-recovery procedures can still cause problems.

1.4 Authentication versus authorization

These concepts are closely related but serve different purposes.

Authentication

“Are you who you claim to be?”

Example: Verifying an employee's login.


Authorization

“What are you permitted to do?”

Example: Allowing that employee to view a specific case file but not delete it.


A user can authenticate successfully and still receive an “Access denied” message because they lack the required authorization.

In a secure application, authorization should be enforced by the server or trusted system—not merely by hiding buttons in the user interface.

1.5 What is access control?

Access control is the process of deciding which identities can access particular resources and which operations they may perform.

Resources can include:

- Files and folders
- Databases
- Applications
- Network services
- Cloud storage
- Digital forensic evidence
- Administrative tools

Typical operations include reading, writing, modifying, deleting and executing.

For example, a digital forensics case-management application might allow an investigator to view evidence assigned to them while restricting evidence deletion to specifically authorized personnel.

1.6 Four important access-control models

These models define different ways to decide access.









A. DAC — Discretionary Access Control

The resource owner can decide who receives access, subject to system rules.

Example: A file owner grants a colleague permission to read a document.

Risk: Permissions may be shared too broadly or granted carelessly.












B. MAC — Mandatory Access Control

Access is governed by centrally enforced security policies and labels, rather than being freely decided by individual owners.

Example: A classified environment permits access based on security clearance and information classification.

Typical use: Highly controlled government or military environments.












C. RBAC — Role-Based Access Control

Permissions are assigned to roles, and users receive permissions through their assigned roles.

Example: An “Investigator” role can access assigned case records, while a “System Administrator” role manages approved system settings.

Benefit: Simplifies administration when many users have similar responsibilities.












D. ABAC — Attribute-Based Access Control

Access decisions use attributes of the user, resource, requested action and sometimes the environment.

Example: An investigator can view a case only if they are assigned to it, the case is active and the device meets the required security policy.

Benefit: Supports fine-grained, context-aware access decisions.



1.7 Comparison of access-control models

Model	Access decision is primarily based on	Example

DAC	Owner-controlled permissions	File owner grants read access

MAC	Central policy and security labels	Clearance-based document access

RBAC	Assigned roles	Lecturer, investigator, administrator

ABAC	Attributes and policy rules	User, case, device and context

These models are not always mutually exclusive. A real system can combine approaches—for example, role-based permissions plus device-compliance conditions.

1.8 Authentication sessions and account security

Authentication often creates a session so the user does not need to prove their identity for every action.

A session may be represented by a session cookie, token or other credential.

Security risks include:

- Session hijacking: An attacker obtains and uses another user's session.
- Credential stuffing: An attacker tries stolen username-password pairs from other breaches.
- Brute-force attacks: Repeated attempts to guess credentials.
- Privilege escalation: An attacker gains greater permissions.
- Broken access control: An application allows actions or data access that the user should not have.

Useful defensive practices include MFA, secure session handling, short-lived or revocable credentials where appropriate, server-side authorization checks, access reviews and monitoring.

1.9 Which model should an organization choose?

The choice depends on its requirements.

- A small team sharing ordinary documents may use DAC-style file permissions.
- A company with departments and standardized job functions may benefit from RBAC.
- A highly classified environment may require MAC.
- A cloud application with decisions based on identity, resource ownership, device compliance and time may use ABAC or a combined model.

There is no single model that is automatically best for every organization. The model must match the sensitivity of the data, operational needs and threat environment.

2. Practical — Explore Windows access control

Time: approximately 25 minutes

Today's lab focuses on examining permissions and relating them to authentication and authorization. Use only your own computer or an environment you are authorized to inspect.

Exercise 1 — Inspect your account identity

Open PowerShell:

whoami

whoami /user



Record what each command reveals:

- whoami identifies the current account.
- whoami /user displays the account's security identifier.

Exercise 2 — Examine folder access permissions

Run:

icacls "$env:USERPROFILE\Desktop"


Identify at least two listed users or groups, if available, and the permissions shown for them.

Remember that the effective permissions can depend on inherited rules, group membership, deny entries and other Windows security mechanisms.

Exercise 3 — Inspect local accounts

Run:

Get-LocalUser |
    Select-Object Name, Enabled


Observe which accounts are enabled or disabled. Do not alter their status.

Exercise 4 — Understand a permission decision

Imagine a forensic lab with these roles:

- Trainee: Read assigned evidence files.
- Investigator: Read and update assigned case records.
- Evidence custodian: Perform approved evidence-management operations.
- Administrator: Manage system configuration and accounts.

For each situation, decide whether the user should be allowed access.
